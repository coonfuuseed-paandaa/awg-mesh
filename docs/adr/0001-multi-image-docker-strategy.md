# ADR-0001: Multi-Image Docker Strategy

## Status

Accepted

## Context

awg-mesh currently ships a single Docker image (`awg-mesh-node`) that runs all three node modes via `--mode` flag. This image:
- Includes `libpcap` for traffic capture (only used by masters)
- Includes `iptables`, `iproute2` (used by all modes)
- Is ~42 MB (Alpine-based)
- Runs as root with `NET_ADMIN` + `NET_RAW` capabilities

For the public release, we need to decide how to package three distinct deployment scenarios:

| Scenario | Mode | Unique Dependencies | Users |
|----------|------|---------------------|-------|
| **MikroTik Smart Client** | `--mode client` | miekg/dns, DSCP routing (nftables) | MikroTik router operators |
| **Linux Client** | `--mode client` | miekg/dns, DSCP routing (nftables) | Linux router/server operators |
| **Master / Endpoint** | `--mode master` or `--mode endpoint` | libpcap (capture), eBPF (forwarding) | Infrastructure operators |

Key constraints:
- MikroTik containers run on RouterOS with limited resources (<50 MB image, <64 MB RAM)
- libpcap + gopacket require CGO — significantly increases binary and image size
- Client mode does NOT need capture or eBPF
- Master and endpoint share 90% of code; splitting them adds maintenance cost for minimal gain

## Decision Drivers

* MikroTik ARM image must be <50 MB and <64 MB runtime memory
* Client binary should build without CGO when capture is disabled
* Minimize maintenance burden — fewer Dockerfiles = fewer drift vectors
* Clear naming for Docker Hub / GHCR discoverability
* Master and endpoint are operationally similar — splitting offers no user benefit

## Considered Options

### Option 1: Single Image (current)

One image `awg-mesh`, mode selected at runtime via `--mode` flag.

- **Pros**: Simplest to maintain, single CI pipeline, single Dockerfile
- **Cons**: Image includes libpcap even for clients, larger than necessary for MikroTik, no CGO-free client option

### Option 2: Two Images — Client + Server

Split into `awg-mesh-client` (no CGO, no libpcap) and `awg-mesh-node` (full, master/endpoint).

- **Pros**: Client image is smaller (~25 MB vs 42 MB), client binary is CGO-free (static, portable), master/endpoint stay unified (they share code), clear naming
- **Cons**: Two Dockerfiles, two CI matrix entries, need build tag for capture

### Option 3: Three Images — MikroTik Client + Linux Client + Server

Separate MikroTik client with ARM focus from Linux client.

- **Pros**: MikroTik image optimized for ARM + size constraints, can handle VETH naming quirk
- **Cons**: More maintenance. However, the MikroTik VETH naming issue (see below) needs runtime handling regardless of image split — it's a code concern, not an image concern.

### Option 4: Single Image + Build Tags

One Dockerfile with multi-stage conditional: `--build-arg VARIANT=client` excludes libpcap.

- **Pros**: Single Dockerfile, CI matrix for variants, DRY
- **Cons**: Build-arg logic adds complexity, Docker layer caching less effective

## Decision

**Option 2: Two Images — Client + Server.**

| Image | Binary | CGO | Build Tag | Includes | Modes |
|-------|--------|-----|-----------|----------|-------|
| `awg-mesh-client` | `awg-mesh-node` | `CGO_ENABLED=0` | `nocapture` | DNS server, DSCP routing stubs | `--mode client` |
| `awg-mesh-node` | `awg-mesh-node` | `CGO_ENABLED=1` | (default) | libpcap, eBPF, DNS, DSCP routing | `--mode master`, `--mode endpoint` |

MikroTik and Linux clients use the SAME `awg-mesh-client` image — the distinction is in router config generation (`mesh-ctl routing generate --platform mikrotik|linux`), not in the container binary.

## Rationale

1. **Client ≠ Server in dependencies**: Client needs DNS + DSCP routing but NOT libpcap/eBPF. Removing CGO drops image size from ~42 MB to ~25 MB and makes the binary fully static.
2. **Master ≈ Endpoint**: Both need libpcap, eBPF, full routing stack. Splitting them creates maintenance burden with no user benefit — mode is a runtime flag.
3. **MikroTik = Linux client**: The container binary is identical. MikroTik's `.rsc` config is generated by `mesh-ctl` on the admin machine, not by the container. A separate MikroTik image would be a clone with a different tag.
4. **CGO-free client**: `nocapture` build tag excludes gopacket/libpcap imports. Client DSCP routing uses nftables (Go library, no CGO). DNS uses miekg/dns (pure Go). Result: static binary, scratch-compatible, ARM-portable.

## Consequences

### Positive

- Client image ~25 MB (from 42 MB) — meets MikroTik <50 MB requirement
- Client binary is static — runs on scratch, distroless, Alpine, any Linux
- Server image unchanged — no regression for existing deployments
- Clear naming: `awg-mesh-client` vs `awg-mesh-node`
- CI matrix: `[client, server]` × `[amd64, arm64]` = 4 builds

### Negative

- Two Dockerfiles to maintain (`deploy/Dockerfile.client`, `deploy/Dockerfile.node`)
- Need `nocapture` build tag and conditional compilation for capture code
- Docker Hub / GHCR now has two image names to document

### MikroTik VETH Interface Discovery (critical runtime concern)

MikroTik RouterOS changed VETH naming behavior:
- **ROS < 7.20**: VETH always appears as `eth0` inside the container
- **ROS ≥ 7.20**: VETH uses the name assigned in RouterOS (e.g., `AMNEZIAWG`)

Reference: https://hub.docker.com/r/wiktorbgu/amneziawg-mikrotik

This means our client container MUST auto-discover its network interface(s) rather than hardcoding `eth0`. Implementation approach:

1. **Enumerate non-loopback interfaces** at startup via netlink (`LinkList()`)
2. **Filter by state UP** and type veth/bridge
3. **Use discovered interface name** for nftables masquerade, DSCP routing, DNS bind
4. **Support multiple interfaces** if client connects to multiple VETHs (multi-master)

This is a CODE change (in `pkg/node/client_linux.go`), not an image split concern. Both MikroTik and Linux clients need interface auto-discovery — Linux containers may also use non-eth0 names (e.g., `veth0`, custom bridge names).

### Risks

- Build tag drift: if new code imports libpcap without the tag guard, client build breaks
- Mitigation: CI builds client with `CGO_ENABLED=0` — any CGO dependency breaks the build immediately
- VETH discovery may find unexpected interfaces in complex Docker networks
- Mitigation: allow `--interface` flag override, fall back to auto-discovery

## Implementation Plan

1. Add `//go:build !nocapture` to `pkg/awggen/capture.go` and `pkg/node/capture_linux.go`
2. Create `deploy/Dockerfile.client` (CGO_ENABLED=0, no libpcap, scratch base)
3. Create `deploy/Dockerfile.node` (rename current Dockerfile)
4. Update CI matrix: build + push both images
5. Update README with two image references
6. Tag existing `awg-mesh` image as `awg-mesh-node` for backwards compatibility
